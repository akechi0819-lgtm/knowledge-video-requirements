# 知识视频蓝图方法论
## 1. 什么算「一个好视频的蓝图」

观众看完能复述出 3 句话，其中**至少 2 句含有具体信息**（年代、地点、数字、机制、证据、事件），而不是 3 句正确的废话。

三个硬判据：

1. **有钩子**：开头抛出一个观众真的会想知道答案的问题，且全片确实回答了它。
2. **有信息增量**：每一段至少给一个观众大概率不知道、且说得出来的事实。
3. **有结构收束**：知识不是并列罗列，要能串成一条因果或时间线，最后回扣开头的场景。

## 1a. 主线是因果链，不是证据清单（事实沙拉也是不合格项）

- **主线 = 一条因果链**（叙事型需求）：通常是「初始状态 → 人为什么介入 → 选择了什么 → 对象发生了什么改变 → 这个改变如何溢出并改写更大的事」。每段「讲什么」写的是这条链上的**下一拍（带因果推进）**，不是「某地发现了某物」。
- **证据是路标，不是主角**：证据的叙事角色是「我们怎么知道」。在故事的关键转折处出现一次、一两句带过，撑住可信度就继续走；不要让段落围着证据组织。
- **判据**：观众看完能复述的应该是**故事**，而不是地名与年代的罗列。

## 2. 先判断需求形态，再谈骨架（反机械化条款）

**方法论是工具箱，不是模板。** 动笔前先读需求，判断三件事：观众是谁、大概多长、这是什么形态——叙事型（历程 / 谜题 / 人物）、盘点型（榜单 / 清单）、概念解释型（从直觉到机制）、教程型……不同形态的主线和拆法完全不同。**本文的骨架与配比是叙事型科普的常见解；需求形态不匹配就不要套；本文任何规则与需求冲突时，一律以需求为准。**

叙事型需求的常见骨架（举例，不是唯一模板）：**钩子 → 反直觉/反差 → 拆解问题 → 机制与证据 → 时间与传播 → 回扣**。

配比原则（v1 写的「通常 3—5 段」是错的，直接导致重头戏被压成一段）：

- 钩子与回扣各占极少段落，**知识主体必须占全片一半以上段落**。判断方法：哪一段在回答标题里那个问题，哪一段就是重头戏；重头戏不许一段带过。
- 知识主体怎么拆：**一个对象一层**、**一个机制一层**或**历程一拍一层**——按需求里的问题结构选，不要机械沿用别的片的拆法。


## 3. 每段字段

| 字段 | 必填 | 写什么 |
|---|---|---|
| `讲什么` | ✓ | 这段要给出的**具体结论**，不是「要讲什么层」 |
| `关键事实` | 可选 | 有可靠依据时提供具体事实；开启质量门槛时按配置必填 |
| `画面意图` | 每段填写 | 写清可见的具体对象及其在本段发生的变化，帮助解释内容；保留用户明确提出的画面要求，不指定动画技术 |
| `旁白` | — | 契约可选。保留创作者提供的旁白；有旁白且未提供原稿时，每段写可直接朗读的口语旁白，创作者明确要求无旁白时留空。**不许用「待创作者补」占位** |
| `备注` | — | 可选。表述边界、待核对项写这里 |

用户明确提出的分镜、旁白、素材或渲染要求应保留；未指定的制作方案由后续制作决定。

「讲什么」可能直接用于配音，应写成自然、可听懂的讲述。出处紧跟对应的关键事实，核查过程留在备注，不在每段讲述或旁白重复脚注、来源或免责声明；必要的不确定性、准确性限定和用户要求的表述边界仍须保留。

整份文档还需：主题（H1 `# 蓝图：<主题>`）、「用户明确要求」列表、叙事顺序。

## 4. 什么叫「硬知识颗粒」

六种类型，任取其一即可，但必须具体到能被复述：

1. **考古 / 实物证据**：某地遗址出土了什么、从什么上面检测出什么。
2. **年代 + 地点**：约多少年前、在哪个具体地区发生了什么。
3. **可量化变化**：从多小变到多大、产量或毒素怎么变、多少年、多少倍。
4. **机制**：为什么会这样（基因位点、选择压力、加工去毒、气候限制）。
5. **文献 / 器物 / 人物**：谁在哪一年记下了什么、哪件器物上画了什么。
6. **事件节点**：某年发生了某件能被记住、能推动传播的事。

**合格判据**：一条 `关键事实` 至少含一个锚点 —— 时间 / 地点 / 数字 / 专名 / 机制 / 证据，且长度 ≥ 15 字。
写出能支撑结论的具体信息。

## 5. 避免占位话术

开启质量门槛时，以下词组出现在 `关键事实` 里会判错；大量出现在 `讲什么` 里会判提醒：

```
以核对后的资料为准 / 待核对 / 具体地区与年代 / 具体年代与遗址名
不自行写死 / 不新增台词 / 讲解文案待创作者 / 本段只讲 / 这一段只负责
该讲哪一层 / 讲到什么颗粒度 / 以…为准 / 观众应能复述 / 让观众有获得感
只给概念印象 / 不宣布具体年代 / 具体内容放到 / 后面会逐层给出
```

它们不是内容，是**关于内容的说明书**。需要标注不确定性时，写进 `备注`（例如「年代取学界估计区间，成片前请核对」），正文照常写具体事实。

## 8a. 联网检索（仅当本次运行明确允许）

默认不联网：先凭自身知识把事实写具体。写不具体、对年代或数字没把握，且本次运行被明确允许检索时，才用 web_search / web_fetch 定向补充。

- 先列缺口（缺什么年代 / 地点 / 证据），定向搜，不漫游；最多 3–5 次检索。
- 搜到的事实**直接写进该段关键事实**，具体到能被复述；来源出处（媒体 / 机构 / 年份）写进备注。
- 检索不给力就别硬凑：宁可少一条事实，不要一条空话。
- 任何情况下不执行命令、不写文件。

## 8b. 场面取证（需求单带本地引用时）

长文 / 小说类需求的原文依据**不在你的上下文里**，也不允许读文件。取证只走 `query_scene(question)` 工具：

- 问题要具体（人物 / 事件 / 物件），一次一句；写进关键事实的原文细节，先查后写。
- `found`：可以作依据。引文写进关键事实时保持原意，来源写备注。
- `candidate`：只是部分线索，**不得当作已印证的答案**；要么改述为不确定表述，要么放弃。
- `not_found`：该索引没有依据 ≠ 原著没有。备注如实写「原文未印证」，不要编引文。
- 索引只收录了筛选过的段落（需求单「本地引用查询」块写明范围），超出范围的内容不查、不猜。

## 9. 提交方式

1. 若本会话尚未加载本 skill 的全文，先调用 `skill` 工具加载 `blueprint`；catalog 里的摘要不是规则正文。
2. 调用 `write_blueprint` 一次性提交结构化蓝图。参数即契约：
   `topic / core / audience / order / userRequirements[] / sections[{id,title,intent,facts[],visual,narration}] / notes`
   — `sections[].facts` 是可选数组；仅在本次配置要求时必填。
3. 工具内置同一个校验器，检查格式，并在开启质量门槛时检查内容质量。失败会把 `errors` 逐条返回；按错误改正后**重新调用工具**，不要在正文里手写一份、不要改编号规则。
4. 不要自己写文件；使用 `read_requirement` / `query_scene` 读取需求与场面依据。只有本次运行明确允许联网时才能使用网页检索。

## 10. 返工规则

创作者按 `B0N` 指出段落 → 意见落到 `outbox/反馈.md` → 同一个 agent 会话接上下文回改 → 出 `vN+1`。

- **反馈说「信息密度低 / 离科普差得远」时，唯一正确的动作是把具体事实写进段落**，不是新增一段「本段将给出证据与变化」。
- 只按反馈调整，保留未受影响的段落内容与编号；删段留空号，插段用 `B03a` 后缀，绝不重排。
- **文件才是唯一真相源**，会话历史不是版本库；会话丢了也能从 `outbox/蓝图_vN.md` 继续。

## 11. 确认与如实标注

创作者逐段确认后可以定稿；`outbox/交付.md` 保存版本、段落索引和完整蓝图，供后续制作参考。
每份产物头部记录 `- **引擎：** …`；`runs/*.json` 记录 `engine / realCall / model / errors / ms`。
生成失败时如实报告，不以离线样例冒充模型生成。
